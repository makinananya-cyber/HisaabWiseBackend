# ADR-0012 — `POST /v1/events` is unauthenticated but bounded by an allowlist and an install id

**Status:** accepted
**Relates to:** Product Spec §8, Technical Spec §4 (`events.userId?`)

## Context

Technical Spec §4 makes `events.userId` optional, and Product Spec §8 wants "registration
completion per step" plus goal-set-versus-skip. The *interesting* half of that funnel is
**abandonment**, which by definition happens before an account exists.

So either the endpoint is open — a free-form write surface with no cost to abuse — or the
activation funnel Product Spec §8 asks for is unobtainable. Closing it entirely would also
mean the first-expense-within-24h activation metric is the only one that survives, and §8
calls the registration funnel out explicitly.

## Decision

**Open, but narrow.**

- **An event-name allowlist**, compiled into the Worker. Any name not on it is rejected.
- **No free-form props.** Each allowlisted name declares its permitted prop keys; unknown
  keys are rejected. The endpoint cannot be used as free storage.
- **An anonymous `installId`**, generated by the client at first launch and sent with
  unauthenticated events.
- **A hard IP rate limit**, via the same binding as
  [ADR-0010](0010-auth-throttling.md).
- **Stitching at registration:** the app sends the `installId` once more with its bearer
  token, so the server can attach pre-auth events to the new `userId`.

Authenticated batches use the bearer token and ignore `installId`.

## Consequences

- The abandonment funnel Product Spec §8 actually asks for is measurable, while the write
  surface stays bounded in both shape and volume.
- Adding a new metric now requires a backend deploy to extend the allowlist. Accepted: it
  also means an event schema can never drift silently, and §8's metric list is fixed and
  known at launch.
- `installId` is an anonymous identifier tied to a device before consent. It is stitched to a
  user only after registration — at which point consent has been given — and is purged with
  the user by `purge:deleted` ([ADR-0007](0007-scheduled-jobs.md)). Worth confirming against
  the PDPL position in the Privacy Policy, since it is collected pre-consent.
